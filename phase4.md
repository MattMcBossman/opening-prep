# Phase 4 — Backend (accounts, repertoire persistence, caching, drill stats)
## Problem statement
Everything through Phase 3 lives in the browser: the repertoire is a `localStorage` blob, the Lichess API token is pasted in by hand and kept client-side, explorer responses are cached only for the lifetime of a tab, and drill results vanish when the session ends. That blocks anything that needs durable or shared state — using the same repertoire on a second device, spaced-repetition scheduling that depends on history, or respecting Lichess's rate limits across users. Phase 4 adds the Django backend that the architecture has always assumed, without taking away the ability to use the app signed out.
## Current state
`frontend/` is a React 19 + Vite + TypeScript app. Repertoire trees are normalized-FEN-keyed maps per color in `src/hooks/useRepertoire.ts`, whose cascade-delete rules (transposition-aware orphan removal, and pruning opponent replies left with no prepared response) are the subtlest logic in the project. Explorer requests go straight from the browser to `explorer.lichess.org` with a user-supplied token (`src/lib/lichessExplorer.ts`), and drill outcomes are session-scoped state in `src/lib/drillSessionLogic.ts`. There was no `backend/` directory at all.
## Scope for this phase
User accounts via Lichess OAuth, server-side repertoire storage, a caching explorer proxy, a FEN-keyed engine-evaluation cache, and persistent drill statistics. Signed-out use keeps working exactly as before, on `localStorage`. Out of scope: player game-history import (Phase 5), gap detection and coverage dashboards (Phase 6), multiple repertoire profiles and overlays (schema is ready for it; no UI), and PGN import/export.
## Stack and local environment
Django 5.2 + Django REST Framework + PostgreSQL 16, dependencies managed by `uv` (`backend/pyproject.toml` + `uv.lock`), linted and formatted with `ruff`, tested with `pytest` + `pytest-django`. Development runs Django on the host for a fast edit/reload/debug loop; `backend/docker-compose.yml` offers a disposable PostgreSQL on port 5433 for anyone who'd rather not install one, and `backend/Dockerfile` builds the production image so prod parity isn't deferred to a later phase. `python-chess` is used only to validate client-submitted FENs and moves.
## Authentication: Lichess OAuth (PKCE), backend-held token
Lichess is a public OAuth client: there is no client secret, `client_id` is just an identifying string, and — importantly — the Opening Explorer requires **no scopes at all**, only that a token exists. The backend owns the whole flow: it generates the `code_verifier`/`state`, stashes them in the Django session, redirects to `https://lichess.org/oauth`, and handles the callback itself, so the access token never reaches the browser. Tokens are encrypted at rest with Fernet (`accounts/crypto.py`) and read only through `accounts.tokens.get_lichess_access_token`, which returns `None` rather than raising for a missing account, an anonymous user, or ciphertext that can't be decrypted — a rotated key degrades one user's explorer requests instead of 500-ing an endpoint.
The SPA authenticates with a session cookie rather than a bearer token, and Vite proxies `/api` to Django in development, which keeps the cookie first-party and means the project needs no CORS configuration whatsoever. Note that with session-only auth DRF answers unauthenticated requests with **403, not 401** (there's no `WWW-Authenticate` challenge to issue); the frontend treats both as "signed out", and reserves 401-from-the-explorer for "signed in but no usable Lichess token".
## Data model
Position identity stays exactly what it is on the client: the normalized FEN. `backend/common/fen.py` is a direct port of `frontend/src/lib/chessUtils.ts` with tests mirroring the Vitest cases, because if the two normalizations ever disagree, transpositions silently split into separate repertoire nodes.
* `accounts.User` — a custom `AbstractUser` created in the very first migration, since swapping `AUTH_USER_MODEL` in later is a migration-rewriting exercise. `LichessAccount` holds the linked identity and encrypted token.
* `repertoire.Repertoire` / `RepertoireMove` — a *collection* of named per-color repertoires (not a hardcoded white/black pair), storing an edge list of `origin_fen -[san/uci]-> resulting_fen`. The edge list is what makes transpositions a single node with several incoming edges, which is precisely what the cascade rules' reachability checks need. Modelling it as a collection now means the deferred "multiple repertoire profiles with overlays" feature needs no migration later.
* `explorer_cache.PositionStatsCache` — keyed by `(source, normalized FEN, params hash)`. The params hash matters: the planned rating-band filter would otherwise be served all-rating data from cache.
* `explorer_cache.EngineLineCache` — one row per normalized FEN and engine build, keeping the *deepest* evaluation seen and shared by explorer/drill clients.
* `drills.DrillSession` / `DrillLineResult` / `DrillAttempt` — raw attempts are the source of truth; per-position weakness aggregates are computed on read rather than denormalized, since a future spaced-repetition scheduler is the real consumer.
## Cascade deletes: one behaviour, two implementations
Removing a repertoire move is not a simple row delete. It must remove the subtree beneath the resulting position *unless* that position is still reachable via another saved line, and then — if the origin is left with no saved moves and it's the owner's turn there — delete the opponent replies leading into it, recursing exactly one step. The mirror case, one of the owner's own moves with nothing prepped underneath yet, is a normal state and must never be pruned.
The server is authoritative for signed-in users, so this logic exists twice: `frontend/src/lib/repertoireTree.ts` (extracted from the hook, still authoritative for anonymous users and for optimistic updates) and `backend/repertoire/cascade.py`, which operates on plain dicts so it can be unit-tested without a database. Both are covered by parity test suites. Divergence between them is a defect by definition.
## Explorer proxy
`GET /api/v1/explorer/stats/` returns the same `ExplorerResponse` shape the client already consumes, so the frontend's types are unchanged. It serves from `PositionStatsCache` when fresh, and otherwise fetches upstream using the signed-in user's stored token, taking a PostgreSQL advisory lock so concurrent requests for the same position produce one upstream call rather than a stampede. Upstream 429s are passed through with `Retry-After`; timeouts and 5xx become 502 rather than a traceback. Anonymous callers with no server token get a 401, and the frontend falls back to its existing direct-to-Lichess path with the pasted token — which is why that UI is preserved rather than deleted.
## Frontend integration
The hook APIs (`getContinuations`/`isMoveSaved`/`addMove`/`removeMove`) are unchanged; the storage behind them is swappable, with a local adapter (existing behaviour) and an API adapter. The API adapter applies optimistic updates through the same pure tree functions and reconciles against the tree the server returns, refetching that color on failure rather than hand-rolling an undo. Saving a move cascades to save every earlier ply, which becomes a single batched request instead of N sequential ones. On first sign-in with a non-empty local repertoire, a one-time import prompt calls the idempotent import endpoint and leaves the local copy untouched.
Drill recording is strictly additive and best-effort: sessions are created on start, attempts flushed in batches, and outcomes posted on finish, with every failure swallowed so that recording can never disturb a drill in progress. `drillSessionLogic.ts` is untouched.
## Testing and validation strategy
Backend: `pytest` covering the OAuth callback (state mismatch, repeat login, token round-trip, and that tokens never appear in a response), cascade parity against the Vitest cases, repertoire API behaviour including ownership, explorer cache hit/miss/expiry/params-isolation/429/502, a threaded single-flight test against real PostgreSQL, keep-deepest upserts, and drill recording and aggregates. All outbound HTTP is mocked; the suite never touches a live API. Frontend: Vitest for the extracted tree functions, API client, auth, explorer routing and fallback, and drill recording. The gate for the phase is `pytest`, `ruff check`, `ruff format --check`, and `makemigrations --check` on the backend, plus `npm run lint`, `npm run test`, and `npm run build` on the frontend.
## Risks and decisions
The cascade duplication is the main long-term hazard: two implementations of subtle logic will drift unless the parity suites are maintained together, and a drift would corrupt repertoires rather than merely erroring. Keying drill history to a repertoire by `ForeignKey` with `CASCADE` means deleting a repertoire discards its statistics — deliberate, since per-position history is meaningless without the lines it refers to, but worth revisiting if repertoire deletion ever becomes routine. `repertoireId` arrives in request bodies, so ownership is checked centrally and rejections are deliberately indistinguishable from "no such repertoire" to avoid an existence oracle. Finally, the engine-eval cache endpoints exist but the client still evaluates and caches purely in-browser; wiring the client to the shared cache is a small, separate follow-up.
