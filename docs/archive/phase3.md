# Phase 3 — Drills (Chessly-style)

> Historical design record. Use `README.md`, `AGENTS.md`, and `ROADMAP.md` for
> current behavior and priorities.

## Problem statement
Add a drill mode that lets a user practice saved repertoire lines from the existing FEN-keyed repertoire tree, get immediate feedback on incorrect moves, and track weak positions without introducing backend/accounts yet.
## Current state
The app is a frontend-only React/Vite app in `frontend/`, with the explorer and repertoire builder wired through `src/App.tsx`. Repertoire data is stored client-side in `src/hooks/useRepertoire.ts` as normalized-FEN keyed trees for White and Black. Move execution and history are centralized in `src/hooks/useGame.ts`, and Stockfish WASM evaluation already exists through `src/hooks/useEngineEval.ts` and `src/engine/stockfishEngine.ts`. There is no dedicated drill route/view, no mistake tracking store, and no automated test suite beyond `npm run build` and `npm run lint`.
## Scope for this phase
Implement Phase 3 entirely in the frontend and localStorage. The deliverable is an MVP drill mode for saved repertoire subtrees, with wrong-move feedback that distinguishes bad moves from off-book playable moves, detects nearby saved/transposed positions by simple piece-placement Hamming distance, and records per-position mistake counts. Backend persistence, account sync, advanced spaced repetition, and server-side caches stay out of scope for this phase.
## Proposed app structure
Introduce a simple mode switch in `src/App.tsx` between Explorer and Drills rather than adding routing. Keep the explorer as the repertoire-authoring surface and add a `DrillPanel`/`DrillBoard` flow that reuses the existing board, move execution, board-color toggle, and engine evaluation UI patterns where possible. Update `README.md` and `AGENTS.md` once Phase 3 behavior and scripts/status change.
## Drill generation: leaf-path enumeration
A repertoire's `RepertoireTree` already stores the full move tree for a color, including opponent replies (see AGENTS.md and `useRepertoire.ts`). Define one "drill" as a single root-to-leaf path through that tree (or a chosen subtree's root, once "drill from current position" is added). A leaf is any node with no further saved continuations. Leaf count in a tree is additive across siblings, never multiplicative, so this stays proportional to the number of lines actually prepped — it does not explode combinatorially even when several branch points exist along the same line. Add `collectDrillLines(tree, rootFen)` in `src/lib/repertoireDrills.ts` that walks the tree and returns one `DrillLine` (ordered list of `{ fen, uci, san, mover: 'own' | 'opponent' }` steps) per leaf. "Drill full repertoire for current color" enumerates leaves from the repertoire root; a later "drill from current explorer position" can reuse the same function rooted at that FEN.
## Handling multiple saved options (the branching problem)
Enumerating one drill per leaf already resolves the ambiguity around multiple saved options without forcing a specific choice or producing an indeterminate drill count:
* At an opponent-turn node with several saved replies, each reply's subtree contributes its own leaves, so every saved opponent reply is guaranteed to appear in at least one queued drill this session — no runtime randomness is needed for correctness, since each drill's path already fixes which reply it auto-plays.
* At the user's own-turn node with several saved options, a given leaf-path designates one of them as "the" expected move for that path, but at runtime **any** saved move from that position is accepted as correct, not just the designated one. If the user plays a different saved option, the session redirects: it treats that move as correct, continues down whichever subtree that move leads into (using the same walk-to-leaf logic), and the original queued leaf-path for the abandoned branch is simply skipped later since its opponent-independent portion was already exercised. This means a user is never penalized for choosing between two moves they've legitimately prepped.
* Net effect: session drill count is deterministic (equal to the leaf count of the tree being drilled), every saved branch gets covered, and no branch is ever presented as "the one correct answer" when multiple are valid.
Given this, the earlier idea of randomly auto-playing among saved opponent replies (with a visible control) is unnecessary for correctness. Replace it with a simpler, purely cosmetic **"Shuffle order" toggle/button** that randomizes the order in which queued drill lines are presented in a session (vs. a fixed, deterministic DFS order) — this is the "visible control" and it affects presentation only, not which lines are included or how they're graded.
## Drill state machine
Create a `useDrillSession` hook, seeded with the queue of `DrillLine`s from `collectDrillLines`, that owns drill state independently of explorer history. It tracks the active line's index/step pointer, current FEN, wrong-attempt count *for the current position within the current line occurrence*, and session-level results. On the user's turn, a legal move is accepted if its UCI matches any saved move from the current position (see above); on the opponent's turn, the hook auto-plays the current line's designated reply. Reaching a step with no further line to follow (a leaf) completes that drill; the session then advances to the next queued line or shows the session summary.
## Correct-move behavior
When the user plays any saved move (whether or not it's the line's originally designated one), show brief positive feedback, advance the position, auto-play the opponent's saved reply if there is one, and continue. Reaching a leaf marks the line complete with zero wrong attempts recorded so far counting as "perfect" for that line (see Mistake tracking).
## Wrong-move feedback
A "wrong" move is a legal move that is not one of the saved moves from the current position (illegal moves are rejected outright, without changing the position, exactly as in the explorer today — they don't count as a wrong attempt). Track a per-position wrong-attempt counter that starts at 0 each time the drill session lands on that position and persists across repeated wrong tries at that same position within this occurrence:
* Compute the centipawn loss of the played move by evaluating the position after the wrong move and comparing it (from the mover's perspective) against the eval at the position before the move. Use a **50 centipawn** threshold to classify severity.
* **1st wrong attempt at this position:** show the move being played, then animate the piece back to its original square. If the cp loss is ≥ 50, additionally show the engine's best response line — i.e. the PV computed from the resulting (post-wrong-move) position, demonstrating how the mistake would be punished — without moving any pieces on the board beyond the revert. If the cp loss is < 50, just revert silently with a lightweight "not the prepared move" indicator and no engine line.
* **2nd wrong attempt at the same position:** repeat the same cp-loss-based feedback as the 1st attempt, and additionally highlight the origin square of the (a) saved move the user should play, so they know which piece to move.
* **3rd+ wrong attempt at the same position:** repeat the same feedback as before, and highlight both the origin square and the destination square of a saved move, fully revealing the move without playing it for them.
* If multiple saved moves exist at this position, the hint highlights are based on one of them (e.g. the line's originally designated move) — any saved move played still counts as correct regardless of which one was hinted.
## Similar/transposed-position hinting
Add utility functions in `src/lib/positionSimilarity.ts` that compare FEN piece-placement strings and compute their **Hamming distance**: expand each FEN's piece-placement digits (run-length-encoded empty-square counts, e.g. "3" meaning three empty squares) into individual empty-square placeholders so both strings represent all 64 squares position-by-position, then count how many of those 64 squares differ between the two positions. A smaller Hamming distance means the two positions are more similar piece-for-piece. On a wrong but legal move, scan saved repertoire positions for the active color and surface the nearest match by this distance when it is within a conservative threshold. If the played move is saved from that similar position, say that the move belongs to a similar/transposed repertoire position and show the saved position's FEN plus the differing squares. Avoid claiming a true transposition unless normalized FENs match exactly; otherwise call it "similar position."
## Mistake tracking
Keep this intentionally simple for the MVP and session-scoped (in-memory React state, not persisted to localStorage yet — persistence can be layered on later alongside Phase 5's spaced repetition). Track, per queued drill line for the current session: whether it was completed with zero wrong attempts across every position in the line ("perfect") or with at least one wrong attempt anywhere along the line ("failed"), regardless of how many retries it eventually took to get right. At the end of a session, show a summary: count of perfect vs. failed lines, and a list of the failed lines (e.g. by opening name/move sequence). Offer a "Retry failed" action that requeues just the failed lines as a fresh session (with wrong-attempt counters reset). This does not mutate the repertoire tree itself.
## UI and components
Add drill-specific components under `src/components/`, likely `ModeToggle`, `DrillControls` (including the "Shuffle order" toggle and Retry-failed action), `DrillFeedback` (cp-loss-based messaging plus the engine's best-response line when shown), and `DrillSummary` (perfect/failed counts and list). Reuse the existing `Chessboard` styling, square-highlighting patterns from `src/App.tsx` (extended with distinct styles for the 2nd/3rd-attempt hint squares), `EvalBar`, and `EngineEvalPanel` rather than duplicating board behavior.
## Engine integration details
The current `useEngineEval` hook evaluates only the currently displayed FEN. Add a small one-shot comparison layer (e.g. a `useEngineComparison` hook or an isolated evaluator method on the Stockfish wrapper) that can: (1) evaluate the position immediately before a wrong move to get a baseline, (2) evaluate the resulting position after the wrong move to compute cp loss and, when ≥ 50cp, extract its PV as the "best response line" to display. Cache comparison results in memory during a session so retrying the same mistake at the same position doesn't restart engine work unnecessarily.
## Testing and validation strategy
Add **Vitest** (plus `@testing-library/react` if component-level tests prove useful) as a dev dependency, with a `test` script in `package.json`. Prioritize unit tests for the pure logic that's easiest to get subtly wrong: `collectDrillLines` (leaf enumeration, correct handling of multiple own-move options and multiple opponent replies, subtree rooting), `positionSimilarity` (Hamming distance calculation, including FEN run-length expansion), and the cp-loss classification helper (50cp threshold boundary behavior). During implementation, also validate with `npm run build` and `npm run lint`. Manual verification should cover: starting a drill with no repertoire, completing a line perfectly, redirecting correctly when an alternate saved move is played, the 1st/2nd/3rd wrong-attempt feedback progression (including the 50cp threshold boundary), similar-position hinting, session summary accuracy, retrying only failed lines, and preserving existing explorer/repertoire behavior.
## Risks and decisions
The largest risk is mixing explorer state and drill state in `src/App.tsx`; keep drill state isolated so practicing cannot accidentally save/remove repertoire moves. Engine comparison can become expensive if every wrong move starts multiple Stockfish searches; use the threshold-based one-shot comparison and in-memory caching described above to bound this. The wrong-attempt counter's reset semantics (per position, per occurrence within a session) should be revisited if playtesting shows it feels off — e.g. whether a "Retry failed" pass should count as a brand-new occurrence (current assumption) or remember prior attempts.
