# opening-prep

## Overview
A web app for building and drilling a personal chess opening repertoire. Primarily inspired by **Chessly (GothamChess)** — particularly its drills mode, where users practice repertoire lines and get feedback on mistakes — with additional inspiration from **openingtree.com** (included as a git submodule at `openingtree/`), which pulls opening statistics for a given player/lines from Lichess and Chess.com game history.

This file is the persistent project reference for Warp/agent-assisted development. Keep it up to date as scope, architecture, and decisions evolve.

Whenever a change in this repo would make `README.md` inaccurate or incomplete (setup steps, scripts, project layout, or overall status/roadmap), update `README.md` in the same change — don't wait to be asked.

## Inspiration source: `openingtree/` submodule
`openingtree/` is a pre-existing React app (CRA-style, React 16, custom webpack scripts) that already implements:
- Lichess and Chess.com API iterators for pulling a player's game history (`src/app/iterator/LichessIterator.js`, `ChessComIterator.js`, `BaseLichessIterator.js`).
- PGN loading/parsing (`src/app/PGNReader.js`, `src/pres/loader/PGNLoader.js`).
- An opening move tree/book built from games (`src/app/OpeningBook.js`).
- Time-control and other filters (`src/pres/loader/AdvancedFilters.js`, `TimeControlLabels.js`).
- Lichess OAuth login flow (`src/edge/lichessloginworker/`).

Treat this submodule as a **reference implementation only**: port the API integration patterns and edge-case handling (pagination, rate limits, time-control filtering) by reimplementing them against the new stack, rather than importing this code directly — it's coupled to an old toolchain (React 16, CRA, its own state layer) that isn't worth carrying forward.

## Key Features

### 1. Opening explorer
- Browse an opening line move by move, with the line/variation name shown (e.g. "Sicilian Defense, Najdorf Variation").
- Engine evaluation (Stockfish or similar) for every position reached.
- Move/result statistics pulled from Chess.com and/or Lichess public APIs for every position (popular next moves, win/draw/loss rates).

### 2. User repertoire builder
- Users save a personal tree-style repertoire, separately for White and Black.
- Only the repertoire owner's own moves are independently toggleable — you can't star an opponent's reply on its own. But saving one of your own moves also saves every earlier ply in that line, including the opponent's replies along the way: e.g. as White, starring 3.Bb5 in 1.e4 e5 2.Nf3 Nc6 3.Bb5 also saves 1.e4, 1...e5 (the opponent continuation you've prepped 2.Nf3 for), 2.Nf3, and 2...Nc6. So the tree really does contain both colors' moves; the UI just never lets the opponent's moves be saved/removed except as a side effect of saving one of your own moves deeper in the line.
- Built directly into the explorer page rather than as a separate viewer: the move list shows the line played so far, then — in the same aligned grid (move number, then the move in the correct White/Black column) — whatever's saved from the current position, so the whole repertoire can be walked just by clicking. The move list's own-move-only save toggle (one star per row, on whichever side holds that color's move) doubles as the removal control for saved continuations. The Lichess explorer table also flags rows already saved to the repertoire (including opponent replies you've prepped a response for), without an equivalent star toggle there.
- Removing a saved move also deletes everything beneath it that's now unreachable — unless a descendant position is still reachable via some other saved line (a transposition into the same position), in which case that shared subtree is kept.
- Removing one of your own moves can also delete its parent: if that was the last of your responses to a given opponent reply, the now-response-less opponent reply is deleted too (recursively bounded to that one step — an opponent reply's own parent, one of your moves, is never deleted this way). The reverse never happens automatically: one of your moves with no opponent reply prepped yet underneath it is a normal, valid state, not something to prune.
- Switching between the White and Black repertoire (the board-color toggle) resets the board and move list, since the two repertoires are unrelated lines.
- No conflict detection: any number of moves may be saved from a given position, forever.
- Per-position view (via the explorer page) shows:
  - Engine evaluation
  - Chess.com/Lichess aggregate statistics
  - Optionally, the user's own stats if they link a Chess.com/Lichess account
- Gap detection: surface repertoire positions that are under-covered relative to real-world move-likelihood stats and/or evaluation (e.g. opponent replies with no prepared response).
- (Long-term) Suggest similar positions already in the repertoire when a gap is found.
- (Long-term) Compare/diff similar positions (similarity heuristic: Hamming distance over piece placement, to start) to highlight key transposable differences.

### 3. Player data via `openingtree` submodule
- Explore a specific player's (e.g. a GM's) games to inspire repertoire choices.
- Analyze the user's own games to find where they deviate from their saved repertoire.
- Support time-range filters: last 24h, last week, last month, last year, all time.

### 4. Drills (Chessly-style)
- Drill mode: pick a branch/subtree of the repertoire to practice.
- On an incorrect move:
  - If it's objectively a bad move, show the engine line explaining why.
  - If it's not bad but simply not the prepared line, say so plainly.
  - If the played move is actually correct in a similar/transposed position, show that position and highlight the differences.
- Track per-position statistics on incorrect attempts to highlight weak spots in the user's preparation.

## Additional Features (Approved)
- **Position identity via FEN, not move order** — key node identity by normalized FEN (+ side to move/castling/ep rights) so transpositions are recognized as the same repertoire node regardless of move order.
- **ECO/opening-name lookup** — resolve line/variation names from an ECO database instead of hand-entry, with manual override. The override input was prototyped in the explorer in Phase 1 but removed as noise there (no repertoire to attach an override to yet); not yet re-added — revisit once there's a natural place to persist an override per repertoire node.
- **Rating-band-aware statistics** — Lichess/Chess.com explorer stats vary a lot by rating bucket; let users filter stats to a relevant rating range rather than only all-time/all-rating aggregates.
- **Repertoire coverage dashboard** — a single view summarizing, per color, % of opponent replies (weighted by real-world frequency) that are covered by a prepared response, not just a raw gap list.
- **Spaced-repetition drilling** — prioritize weak/incorrect lines more often in drill sessions (Anki-style scheduling) instead of uniform random selection.
- **Move/position annotations** — free-text notes per repertoire node (why this move, traps, plans), shown in explorer and drills.
- **PGN import/export** — import existing repertoires from PGN/Lichess studies/ChessBase exports; export the repertoire as annotated PGN. Shipped for plain PGN with RAV variations (see the roadmap's "PGN import/export" entry); Lichess-study/ChessBase-specific import and annotation-comment round-tripping are still open.
- **Multiple repertoire profiles** — e.g. separate prep for different time controls or anticipated opponent styles.
- **Client-side engine via WASM Web Worker** — run Stockfish (or similar, e.g. lc0 if feasible) fully client-side in a Web Worker for evaluation, avoiding server compute cost; consider an optional server-side eval cache keyed by FEN to avoid recomputing common positions.
- **API response caching layer** — cache Chess.com/Lichess explorer responses (keyed by FEN) to respect rate limits and speed up repeated exploration of popular positions; also cache computed engine lines (eval + best/refutation line) for moves flagged as mistakes in drills, so repeated wrong moves don't require recomputation.
- (Long-term) **Play vs. bot** — play out a game against an engine bot of configurable skill level, starting from any selected position (e.g. an explorer/repertoire node), to test lines interactively beyond scripted drills.

## Architecture Direction (Decided)
- **Frontend**: React, with `react-chessboard` for the board (MIT license, native React integration, built-in arrow/shape support for engine lines and position-diff highlighting — chosen over `chessground` mainly to avoid its GPL-3.0 license) and `chess.js`-equivalent move/FEN logic — independent of `openingtree`'s CRA/React 16 stack.
- **Engine**: Stockfish compiled to WASM, run in a Web Worker, no server dependency for evaluation. Use iterative deepening: a fast shallow pass for snappy browsing, continuing to deepen in the background while a position stays selected, with a deeper/longer pass when drills need to explain a mistake; cache the deepest result reached per FEN(+move).
- **Audio**: move sounds are synthesized at runtime with the Web Audio API (`src/audio/soundPlayer.ts`), not shipped as audio files — no binary assets to license, bundle, or fetch, and each cue is a handful of tunable numbers. Four SAN-derived move cues (regular move, capture, check, checkmate) are chosen from the move's SAN (`src/lib/moveSounds.ts`) with precedence checkmate > check > capture > move, so a move that is several at once only plays its most significant cue. Drills also have a distinct drill-complete chime separate from move SAN. Move and capture are short, lowpass-filtered noise+tone "taps" tuned for a percussive, wooden feel rather than an audible pitch sweep, closer to other chess apps' click; check is a warm single ding rather than an alarm-like rising two-tone. A single shared `AudioContext` is created lazily on the first cue and routed through a `DynamicsCompressorNode` limiter (so brief overlapping cues can't clip into distortion), since browsers suspend contexts not created during a user gesture. Because not every cue plays from directly inside a gesture handler - drilling Black can auto-play its first move from a timer before the user has made one of their own (see `AUTO_PLAY_DELAY_MS` in `useDrillSession`) - `installAudioUnlock()` primes (creates + resumes) the shared context on the page's very first pointer/keyboard interaction, whatever it is, rather than relying solely on a move-triggered resume. Sounds fire only for moves that actually land on the board — in drills, a rejected attempt stays silent; completing a drill line plays the final move's cue plus the drill-complete chime. Swapping in sampled recordings later should only touch `soundPlayer.ts`.
- **Backend**: Django + Django REST Framework + PostgreSQL (`backend/`), for user accounts, saved repertoires, drill statistics, and the FEN-keyed cache table for Chess.com/Lichess/engine-line lookups. Django admin doubles as a dev-time inspector for cached data and repertoire trees. Session-cookie auth (not tokens) via DRF's `SessionAuthentication`; unauthenticated requests to authenticated endpoints get DRF's default 403, not 401, which the frontend treats identically to signed-out. The repertoire's cascade-delete semantics (transposition-aware orphan pruning, one-step responseless-opponent-reply deletion) are ported line-by-line from the frontend's `repertoireTree.ts` (`backend/repertoire/cascade.py`), covered by parity tests against the same cases as the Vitest suite. The full OpenAPI schema is annotated with `drf-spectacular` (`@extend_schema` on every view) and served interactively at `/api/v1/docs/`. Signed-out users still get the Phase 2 client-only experience — the repertoire falls back to `localStorage` (keyed by normalized FEN per color) when there's no session, and the frontend migrates it into the backend via a one-time import once the user signs in.
- **Data sources**: Chess.com Published-Data API and Lichess API (opening explorer + account OAuth), reusing patterns from `openingtree/src/app/iterator/*`. As of 2026, Lichess requires a personal API token (Bearer auth) on every Opening Explorer request (endpoint moved to `explorer.lichess.org`). Account linking now exists (Phase 4): signing in with Lichess (PKCE OAuth, no client secret) stores the token encrypted server-side (Fernet, `backend/accounts/tokens.py`) and the explorer proxy (`backend/explorer_cache/`) uses it automatically, with a Postgres advisory-lock single-flight per FEN so concurrent requests for the same position share one upstream fetch. Signed-out users still paste a personal token client-side (stored in `localStorage`) and call Lichess directly, as in Phase 1; the frontend falls back to this path on a 401 from the proxy.

## Development Roadmap
Tracks implementation progress. Check off a phase once it has shipped; update sub-items as needed. Decision: keep Phases 5-6 as single phases for now, revisit splitting if either grows unwieldy.

### Must review before Phase 5
Before starting Phase 5, review and resolve these Phase 2/3 design notes:
- **Position-keyed repertoire storage may be causing repertoire-building friction.** The current normalized-FEN keyed model is good for transpositions, but it may be making some authoring/editing flows harder than expected. Re-evaluate whether the UI/state model needs an additional move-order/tree-path layer on top of the FEN graph before building player-data import/deviation analysis on it.
- **Multiple saved repertoires with overlap and overlays.** Defer this until true backend persistence exists. Once repertoires are backend-backed, users should be able to create multiple separate repertoire profiles/collections that may overlap in positions and lines, then select multiple repertoires to overlay in the explorer/drill views.
- **Drill from selected position.** Users should be able to start drills from a selected repertoire/explorer position. When doing so, include only drills/leaf lines that pass through that position. Provide two drill-start modes: (1) skip straight to the selected position for every drill, or (2) start from move 1 so the user still gets reps for the line leading up to that selected position.

- [x] **Phase 0 — Project setup**: scaffold the frontend app, minimal backend/DB schema, chess.js + board wiring.
- [x] **Phase 1 — Opening explorer (MVP)**: line browser (the Back/Forward controls under the board are also bound to the left/right arrow keys, via `useHistoryKeyboardNav` - suppressed while a text field has focus so the Lichess token input keeps normal caret movement), Lichess explorer stats (cached by FEN, requires a user-supplied Lichess API token), Stockfish WASM evaluation (iterative deepening), opening name from Lichess explorer response (no manual override here — see "ECO/opening-name lookup" above). Chess.com explorer stats not yet integrated (Lichess-only for now).
- [x] **Phase 2 — Repertoire builder**: FEN-keyed repertoire tree per color (normalized-FEN identity for transpositions), built directly into the explorer page (own-move-only save toggle in the move list that cascades to save every earlier ply including opponent replies, saved continuations merged into the same move-list grid, Lichess-explorer annotation), `localStorage` persistence. Removing a move cascades to delete now-unreachable descendants (preserving shared transpositions) and, if that leaves an opponent reply with no response of yours left, that reply too. Toggling White/Black repertoire resets the board. No conflict detection — unlimited branches per position.
- [x] **Phase 3 — Drills (Chessly-style)**: a Drills mode alongside the explorer, isolated from explorer/repertoire-editing state. A drill session enumerates one "line" per leaf (root-to-leaf path) of the repertoire tree for the active color — leaf count is additive across branches, not multiplicative, so multiple saved options at a branch point don't blow up the drill count or force a single "correct" answer: any saved move is accepted if it still leads to a not-yet-completed branch, and playing an alternate valid option redirects the session onto that branch instead of failing, while the abandoned branch stays queued for a later pass. If the user chooses a saved move whose branch has already been fully completed during the current session, the move is rejected and snapped back without counting as a failed drill, forcing practice of the still-pending branch. Progress is tracked per leaf (not per occurrence) via a pending set, with a live "Drill X of Y" readout; after choosing "Retry failed", the retry pass only counts failed lines and reads "Retrying failed drill X of Y." The target line is deliberately not shown, since that would spoil the drill. Presentation order is always shuffled automatically when starting a session, restarting, and retrying failed lines; there is no manual shuffle control. The user's own move and its auto-played opponent reply are applied as two separate state transitions, not one (`pendingAutoPlayStep`/`advanceAutoPlay` in `drillSessionLogic.ts`), with `useDrillSession` re-applying the opponent's reply ~320ms later - long enough for react-chessboard's own move animation (300ms) to finish - so the board animates each ply individually instead of jumping two plies at once, which read as an abrupt jump rather than a smooth slide. Completing a drill line pauses at the final position, plays the drill-complete sound, draws an arrow for the engine's best opponent try from that unprepared leaf, shows the engine continuation line, and waits for the user to choose "Next drill" or "Finish" before advancing. That review also brings in the two per-position views the explorer has, for the position the line ended in: the engine's evaluation (an eval bar beside the board, plus score/depth in the panel) and the Lichess explorer statistics, rendered read-only since the board is paused. Both are deliberately scoped to the pause - a live eval bar or move statistics mid-drill would hint at the prepared move - and the explorer request is skipped outright for every position walked through on the way (`useExplorerStats`'s `enabled` flag) rather than fetched and hidden. Since drill positions are keyed by normalized FEN, the leaf is expanded back into a complete FEN first (`denormalizeFen`, taking the move number from the tracked leaf ply) before it's handed to Stockfish or the Lichess explorer. Wrong moves (legal but unsaved) are classified via a one-shot Stockfish comparison of the position before/after the move, using a 50 centipawn-loss threshold to distinguish objectively bad moves (shown with the engine's best-response line) from merely off-book ones; the piece reverts either way (via react-chessboard's own snap-back), and repeated wrong attempts at the same position progressively reveal the correct move's origin square (2nd attempt) and destination square (3rd+). A Hamming-distance-based position-similarity check (`positionSimilarity.ts`) flags when a near-identical position elsewhere in the repertoire has the played move saved, as a transposition hint. Mistake tracking is intentionally simple for this phase: session-scoped (not persisted) perfect-vs-failed tracking per line, shown in an end-of-session summary with a "Retry failed" action. Core session logic (`drillSessionLogic.ts`, `repertoireDrills.ts`, `positionSimilarity.ts`, `moveQuality.ts`) is unit-tested with Vitest.
- [x] **Move sounds** (cross-cutting, not a phase): distinct synthesized cues for a regular move, capture, check, and checkmate on both the explorer and drill boards, with a header mute toggle persisted in `localStorage` — see "Audio" under Architecture Direction. Previously inconsistent (a delayed, timer-triggered cue - notably drilling Black's auto-played opening move - could silently fail to ever resume a suspended `AudioContext`, and overlapping cues could clip); fixed via `installAudioUnlock()`'s gesture-priming and a limiter, and the move/capture cues were retuned to a shorter, more percussive shape. Sampled recordings are still on the table if the synthesized cues don't hold up.
- [x] **Phase 4 — Backend (Django + DRF + PostgreSQL)**: `backend/` app with a custom `User` model (Lichess OAuth PKCE login, no client secret, no scopes required beyond token existence; access tokens encrypted at rest via Fernet and never serialized to the client), server-side repertoire persistence (`repertoire/` app, cascade-delete semantics ported line-by-line from `repertoireTree.ts` with matching parity tests), a FEN-keyed explorer/engine-eval cache (`explorer_cache/`, single-flight per FEN via a Postgres advisory lock, 429/502 passthrough for Lichess rate-limits/outages, keep-deepest upsert for engine lines), and drill session/attempt/finish endpoints plus per-position weakness aggregates (`drills/`, `DrillSession.repertoire` a real FK with an ownership check that answers "no such repertoire" identically for absent or cross-user ids). Session-cookie auth via DRF's `SessionAuthentication` (403, not 401, when signed out — the frontend treats both as signed-out). The frontend is sign-in-aware: repertoire storage transparently switches between the backend and the Phase 2 `localStorage` fallback depending on auth state, with a one-time import endpoint to migrate an existing local repertoire on first sign-in, and the explorer proxy falls back to the client-side Lichess-token flow on a 401. Full OpenAPI schema (`drf-spectacular`, every view annotated with `@extend_schema`) served at `/api/v1/docs/`. See `phase4.md` for the full design writeup.
- [x] **PGN import/export** (cross-cutting, not a phase): export a per-color repertoire tree as PGN movetext with RAV variations for every saved branch point (`frontend/src/lib/pgnExport.ts`), and import a PGN (with or without variations) back in (`frontend/src/lib/pgnImport.ts`), both wired into a `PgnImportExportPanel` in the explorer's side column. Frontend-only - no backend changes - since import just replays parsed edges through `useRepertoire`'s existing `addMove` (which already routes to `localStorage` or the backend depending on sign-in state and batches same-tick calls), and export reads the full tree via a new `getTree(color)` accessor. Import uses a hand-rolled recursive-descent movetext tokenizer rather than a dependency or chess.js's own PGN API - chess.js parses RAV internally but its public `loadPgn`/`.pgn()` only ever read or write a single mainline, discarding every variation - combined with a `Chess` instance per branch point for SAN legality and FEN/UCI derivation. Export's DFS treats the first-saved move at each position as the mainline and every other saved move as a nested `(...)` variation; a transposition reached via a different line is deliberately duplicated (not linked via FEN comments - unnecessary for round-tripping through our own importer, since normalized-FEN keying already merges transpositions for free on import), and a per-path (not global) visited-FEN guard stops a genuine repetition from recursing forever. Import is additive/idempotent (only ever adds edges), so importing into a non-empty repertoire, or the same PGN twice, is always safe. Comments, NAGs, and Lichess-study/ChessBase-specific import are out of scope for v1 (see "PGN import/export" under Additional Features).
- [ ] **Phase 5 — Player data via `openingtree`**: port Lichess/Chess.com game iterators + PGN parsing, time-range filters, GM-inspiration browsing and own-game deviation analysis. **Partially shipped**: signed-in users can switch the explorer panel (`ExplorerSourceToggle`) to "My games", which shows opening-tree-style move stats built from their own Lichess games instead of the public database, scoped to the active board color. This reuses Lichess's own player-scoped Opening Explorer (`GET https://explorer.lichess.org/player`) rather than importing/parsing individual games - `backend/explorer_cache/player_stats.py` proxies it live (deliberately uncached, unlike `/explorer/stats/`, since it's per-user data), draining its ND-JSON stream (Lichess indexes a player's games in the background, so responses arrive as a sequence of `queuePosition`-tagged lines converging on a final result) up to a ~15s budget and returning a `stillIndexing` flag with a best-effort partial result if that budget runs out before Lichess finishes. Still open: Chess.com as a source, GM/other-player lookup, time-range filters, and comparing games against the saved repertoire to find deviations.
- [ ] **Phase 6 — Gap detection & long-term features**: repertoire coverage dashboard, similar-position suggestions/diffing, spaced repetition, multiple profiles, play-vs-bot from a selected position.
