# Mainline

## Overview
A web app for building and drilling a personal chess opening repertoire. Primarily inspired by **Chessly (GothamChess)** — particularly its drills mode, where users practice repertoire lines and get feedback on mistakes — with additional inspiration from **openingtree.com** (included as a git submodule at `openingtree/`), which pulls opening statistics for a given player/lines from Lichess and Chess.com game history.

The product name is **Mainline**. Legacy technical identifiers remain
`opening-prep`/`opening_prep` where changing them would break browser storage,
PGN metadata compatibility, OAuth configuration, database setup, Django module
paths, or deployment scripts. New user-facing copy should say Mainline; do not
rename those compatibility identifiers without an explicit migration plan.

This file is the persistent project reference for Warp/agent-assisted development. Keep it up to date as scope, architecture, and decisions evolve.

Whenever a change in this repo would make `README.md` inaccurate or incomplete (setup steps, scripts, project layout, or overall status/roadmap), update `README.md` in the same change — don't wait to be asked.

## PostgreSQL checks from Codex

The laptop PostgreSQL 16 cluster runs on `127.0.0.1:5432`; `backend/.env`
targets that host service. Codex's default command sandbox uses an isolated
network/process namespace, so `localhost:5432` inside a sandboxed command does
**not** reach the laptop service. Symptoms include `psycopg.OperationalError`,
`pg_lsclusters` misleadingly showing the cluster as down/owned by `nobody`, and
`systemctl` failing to connect to the bus. These symptoms must not be reported
as “PostgreSQL is unavailable” without a host-level check.

For PostgreSQL-backed tests or diagnostics, run the relevant command with
escalated/host execution. First verify read-only with `systemctl is-active
postgresql`, `pg_lsclusters`, and a `psql` connection using the configured
database. Do not start, restart, reconfigure, or replace PostgreSQL merely
because a sandboxed connection failed. The Compose database on port 5433 is an
optional alternative only when `DATABASE_URL` is deliberately changed to use
it; do not assume Compose is the active database.

## Inspiration source: `openingtree/` submodule
`openingtree/` is a pre-existing React app (CRA-style, React 16, custom webpack scripts) that already implements:
- Lichess and Chess.com API iterators for pulling a player's game history (`src/app/iterator/LichessIterator.js`, `ChessComIterator.js`, `BaseLichessIterator.js`).
- PGN loading/parsing (`src/app/PGNReader.js`, `src/pres/loader/PGNLoader.js`).
- An opening move tree/book built from games (`src/app/OpeningBook.js`).
- Time-control and other filters (`src/pres/loader/AdvancedFilters.js`, `TimeControlLabels.js`).
- Lichess OAuth login flow (`src/edge/lichessloginworker/`).

Treat this submodule as a **reference implementation only**: port the API integration patterns and edge-case handling (pagination, rate limits, time-control filtering) by reimplementing them against the new stack, rather than importing this code directly — it's coupled to an old toolchain (React 16, CRA, its own state layer) that isn't worth carrying forward.

## Key Features

### 1. Opening explorer
- Browse an opening line move by move, with the line/variation name shown (e.g. "Sicilian Defense, Najdorf Variation").
- Engine evaluation (Stockfish or similar) for every position reached.
- Move/result statistics pulled from Chess.com and/or Lichess public APIs for every position (popular next moves, win/draw/loss rates).

### 2. User repertoire builder
- Users save a personal tree-style repertoire, separately for White and Black.
- Only the repertoire owner's own moves are independently toggleable — you can't star an opponent's reply on its own. But saving one of your own moves also saves every earlier ply in that line, including the opponent's replies along the way: e.g. as White, starring 3.Bb5 in 1.e4 e5 2.Nf3 Nc6 3.Bb5 also saves 1.e4, 1...e5 (the opponent continuation you've prepped 2.Nf3 for), 2.Nf3, and 2...Nc6. So the tree really does contain both colors' moves; the UI just never lets the opponent's moves be saved/removed except as a side effect of saving one of your own moves deeper in the line.
- Built directly into the explorer page rather than as a separate viewer: the move list shows the line played so far, then — in the same aligned grid (move number, then the move in the correct White/Black column) — whatever's saved from the current position, so the whole repertoire can be walked just by clicking. The move list's own-move-only save toggle (one star per row, on whichever side holds that color's move) doubles as the removal control for saved continuations. The Lichess explorer table also flags rows already saved to the repertoire (including opponent replies you've prepped a response for), without an equivalent star toggle there.
- Removing a saved move also deletes everything beneath it that's now unreachable — unless a descendant position is still reachable via some other saved line (a transposition into the same position), in which case that shared subtree is kept.
- Removing one of your own moves can also delete its parent: if that was the last of your responses to a given opponent reply, the now-response-less opponent reply is deleted too (recursively bounded to that one step — an opponent reply's own parent, one of your moves, is never deleted this way). The reverse never happens automatically: one of your moves with no opponent reply prepped yet underneath it is a normal, valid state, not something to prune.
- Switching between the White and Black repertoire (the board-color toggle) resets the board and move list, since the two repertoires are unrelated lines.
- **Single-response module invariant:** within one module, every position where the repertoire side is to move may contain at most one saved move. Opponent-to-move positions may branch freely. A composed profile may show several repertoire responses at the same position only when they come from different enabled modules or pinned releases. Saving a conflicting response must offer to replace the existing response/subtree or use another module; imports and gap filling must preview conflicts and may skip them, replace them explicitly, or create a separate module—never silently merge two repertoire responses into one module.
- Per-position view (via the explorer page) shows:
  - Engine evaluation
  - Chess.com/Lichess aggregate statistics
  - Optionally, the user's own stats if they link a Chess.com/Lichess account
- Gap detection: surface repertoire positions that are under-covered relative to real-world move-likelihood stats and/or evaluation (e.g. opponent replies with no prepared response).
- (Long-term) Suggest similar positions already in the repertoire when a gap is found.
- (Long-term) Compare/diff similar positions (similarity heuristic: Hamming distance over piece placement, to start) to highlight key transposable differences.

### 3. Player data via `openingtree` submodule
- Explore a specific player's (e.g. a GM's) games to inspire repertoire choices.
- Analyze the user's own games to find where they deviate from their saved repertoire.
- Support time-range filters: last 24h, last week, last month, last year, all time.

### 4. Drills (Chessly-style)
- Drill mode: pick a branch/subtree of the repertoire to practice.
- On an incorrect move:
  - If it's objectively a bad move, show the engine line explaining why.
  - If it's not bad but simply not the prepared line, say so plainly.
  - If the played move is actually correct in a similar/transposed position, show that position and highlight the differences.
- Track per-position statistics on incorrect attempts to highlight weak spots in the user's preparation.

## Additional Features (Approved)
- **Position identity via FEN, not move order** — key node identity by normalized FEN (+ side to move/castling/ep rights) so transpositions are recognized as the same repertoire node regardless of move order.
- **ECO/opening-name lookup** — public Lichess lookups provide statistical classification and fallback names. `MainlineOpeningName` is the global normalized-FEN-keyed preferred-name layer: curated names take precedence over Lichess wording across transpositions, with optional ECO, reference URL, and curator notes managed in Django admin. ECO codes remain internal metadata and are not shown before names in the explorer or drills. Prefer descriptive human names; move notation is a last-resort inherited-name suffix, not the desired vocabulary. While a new position's lookup is pending, retain the last settled name instead of replacing it with loading copy or an empty label.
- [ ] **Curate common unnamed opening positions (backburner)** — traverse outward from the initial position using public-Lichess move frequencies, rank positions at or above the 250,000-game naming threshold that still resolve through an ancestor-plus-moves fallback, and research/add descriptive `MainlineOpeningName` records for them. Review the highest-volume positions first, preserve source/reference URLs, and prefer established human terminology over invented move-code labels. Unnamed positions below the threshold inherit the nearest ancestor's complete resolved label—including its ancestor-plus-moves suffix when applicable—without appending their own low-volume moves. A native Lichess or curated name remains valid at any volume.
- **Rating-band-aware statistics** — Lichess/Chess.com explorer stats vary a lot by rating bucket; let users filter stats to a relevant rating range rather than only all-time/all-rating aggregates.
- **Repertoire coverage dashboard** — the selected module's headline coverage is `matching games across distinct prepared leaves / matching games at the module's listed opening position`; when its lines split before that listed depth, the latest common ancestor supplies the denominator. The supporting gap analysis uses a 95% practical target, separates fully covered, partially covered, and no-data opponent positions, and ranks positions by uncovered matching games adjusted for the repertoire side's cached engine advantage. Equal or worse positions retain their full exposure; favorable positions are progressively discounted, and missing evaluations remain neutral instead of launching a large batch of client searches. The remaining redesign work adds per-reply gap details, minimum-sample reliability, and explicit rare-tail treatment. See `profile-modules-plan.md` for the detailed notes.
- **Spaced-repetition drilling** — prioritize weak/incorrect lines more often in drill sessions (Anki-style scheduling) instead of uniform random selection.
- **Move/position annotations** — free-text notes per repertoire node (why this move, traps, plans), shown in explorer and drills.
- **PGN import/export** — import existing repertoires from PGN/Lichess studies/ChessBase exports; export the repertoire as annotated PGN. Shipped for plain PGN with RAV variations (see the roadmap's "PGN import/export" entry); Lichess-study/ChessBase-specific import and annotation-comment round-tripping are still open.
- **Opening modules with a retained profile backend** — reusable, color-specific personal opening modules remain the user-facing unit. Profile tables/APIs are retained as compatibility groundwork, but the frontend currently exposes one combined module collection per account while profile composition is redesigned. Migration `0009` consolidates existing memberships and pinned releases into one Default profile without deleting modules or lines. Stable explicit `RepertoireLine`/`RepertoireLineStep` rows preserve move-order paths; authored personal/global paths feed drills with source provenance; and selected-position drills support both skipping to that position and starting from move one.
- **Global opening library** — publish immutable, versioned opening-module releases (Vienna Game, Stonewall Attack, Sicilian Defense, etc.) in clearly separated official Mainline and community-published catalogs. “Load” always opens an immutable read-only module view without writing user data; from that view, users may explicitly attach it read-only to a profile, copy/fork it into a new editable personal module, or review and fill non-conflicting missing lines into the selected module. Gap filling should offer either a complete module or only missing lines, with clear provenance and no silent updates to a pinned release.
- (Long-term) **Shareable module links** — give every published module a stable public URL that can be shared directly. The page should identify the publisher and official/community status, open a specific immutable release by default, allow browsing without signing in, and offer signed-in users clear read-only attach and editable-copy actions.
- **Client-side engine via WASM Web Worker** — run Stockfish (or similar, e.g. lc0 if feasible) fully client-side in a Web Worker for evaluation, avoiding server compute cost; consider an optional server-side eval cache keyed by FEN to avoid recomputing common positions.
- **API response caching layer** — public Lichess explorer responses use a normalized-FEN/filter-keyed 24-hour PostgreSQL cache plus a normalized-FEN 10-minute browser cache. “My games” follows openingtree's client-index pattern: authenticated backend endpoints stream linked-account Lichess/Chess.com game records without retaining them, a Web Worker incrementally parses them into a FEN-keyed aggregate graph, and IndexedDB persists that graph per Mainline user. The worker checkpoints after each source, before a rate-limit wait, and on export failure so partial progress survives reloads; sessionStorage is intentionally not used because its small quota cannot hold large player indexes. Position changes then query the local graph immediately and consume no PostgreSQL space. Stockfish results share a normalized-FEN/build-keyed browser cache across explorer and drill consumers; signed-in clients read/write the backend keep-deepest cache, so revisits and repeated wrong-move origins avoid recomputation. Structured backend cache events and browser counters expose hits, misses, upstream calls, analyses, cancellations, and completions.
- **Mobile-friendly, mobile-oriented UX** — treat phones as a first-class way to build and drill a repertoire, with responsive board/panel layouts, touch-friendly controls, sensible portrait and landscape behavior, and performance testing on mobile-class devices. Start with a high-quality responsive web app; evaluate installable PWA behavior and a dedicated mobile app only after the core mobile web experience is proven.
- **Remote development hosting, then production** — first make the laptop-hosted development stack privately reachable from the developer's phone through free Tailscale Personal and Tailscale Serve; PostgreSQL remains local and no Render service is required. Revisit managed production hosting only when independent uptime or external users matter. Backup/restore engineering is a way-back-burner goal.
- (Long-term) **Play vs. bot** — play out a game against an engine bot of configurable skill level, starting from any selected position (e.g. an explorer/repertoire node), to test lines interactively beyond scripted drills.

## Architecture Direction (Decided)
- **Drill practical-result feedback**: only after a wrong drill move, fetch the public Lichess result sample for its origin position and match the attempted UCI move. Show the drilling side's loss rate and the position baseline only with at least 200 games from the position and 30 games containing that move. Label this as historical correlation; Stockfish remains the source of “objectively bad” claims.
- **Frontend**: React, with `react-chessboard` for the board (MIT license, native React integration, built-in arrow/shape support for engine lines and position-diff highlighting — chosen over `chessground` mainly to avoid its GPL-3.0 license) and `chess.js`-equivalent move/FEN logic — independent of `openingtree`'s CRA/React 16 stack.
- **Engine**: Stockfish compiled to WASM, run in a Web Worker, no server dependency for evaluation. Use iterative deepening: a fast shallow pass for snappy browsing, continuing to deepen in the background while a position stays selected, with a deeper/longer pass when drills need to explain a mistake; cache the deepest result reached per FEN(+move).
- **Audio**: move sounds are synthesized at runtime with the Web Audio API (`src/audio/soundPlayer.ts`), not shipped as audio files — no binary assets to license, bundle, or fetch, and each cue is a handful of tunable numbers. Four SAN-derived move cues (regular move, capture, check, checkmate) are chosen from the move's SAN (`src/lib/moveSounds.ts`) with precedence checkmate > check > capture > move, so a move that is several at once only plays its most significant cue. Drills also have a low descending corrective cue for rejected moves and a distinct drill-complete chime. Move and capture are short, lowpass-filtered noise+tone "taps" tuned for a percussive, wooden feel rather than an audible pitch sweep, closer to other chess apps' click; check is a short, low-pass-filtered 440/660 Hz knock-chime rather than a bright or alarm-like notification. A single shared `AudioContext` is created lazily on the first cue and routed through a `DynamicsCompressorNode` limiter (so brief overlapping cues can't clip into distortion), since browsers suspend contexts not created during a user gesture. Because not every cue plays from directly inside a gesture handler - drilling Black can auto-play its first move from a timer before the user has made one of their own (see `AUTO_PLAY_DELAY_MS` in `useDrillSession`) - `installAudioUnlock()` primes (creates + resumes) the shared context on the page's very first pointer/keyboard interaction, whatever it is, rather than relying solely on a move-triggered resume. Accepted moves fire their SAN cue only when they land; a rejected drill move stays in place, plays the corrective cue once, and highlights its attempted origin/destination light red. Completing a drill line plays the final move's cue plus the drill-complete chime. Swapping in sampled recordings later should only touch `soundPlayer.ts`.
- **Backend**: Django + Django REST Framework + PostgreSQL (`backend/`), for user accounts, saved repertoires, drill statistics, and the FEN-keyed cache table for Chess.com/Lichess/engine-line lookups. Django admin doubles as a dev-time inspector for cached data and repertoire trees. Session-cookie auth (not tokens) via DRF's `SessionAuthentication`; unauthenticated requests to authenticated endpoints get DRF's default 403, not 401, which the frontend treats identically to signed-out. The repertoire's cascade-delete semantics (transposition-aware orphan pruning, one-step responseless-opponent-reply deletion) are ported line-by-line from the frontend's `repertoireTree.ts` (`backend/repertoire/cascade.py`), covered by parity tests against the same cases as the Vitest suite. The full OpenAPI schema is annotated with `drf-spectacular` (`@extend_schema` on every view) and served interactively at `/api/v1/docs/`. Signed-out users get versioned `localStorage` profiles and reusable color-specific opening modules through the same management UI; the frontend can migrate the active local composition into the backend via a one-time import once the user signs in.
- **Authentication**: Mainline accounts are created only through Google authorization-code OpenID Connect. Lichess OAuth is an optional linked chess-data identity after Mainline sign-in; it never creates or signs into a Mainline account. Its encrypted token powers explorer and player-game features. Legacy email-identity/magic-link tables remain for migration compatibility, but no email sign-in routes or UI are active.
- **Data sources**: Chess.com Published-Data API and Lichess API (opening explorer + account OAuth), reusing patterns from `openingtree/src/app/iterator/*`. As of 2026, Lichess requires a personal API token (Bearer auth) on every Opening Explorer request (endpoint moved to `explorer.lichess.org`). Linking Lichess after Mainline sign-in (PKCE OAuth, no client secret) stores the token encrypted server-side (Fernet, `backend/accounts/tokens.py`) and the explorer proxy (`backend/explorer_cache/`) uses it automatically, with a Postgres advisory-lock single-flight per FEN so concurrent requests for the same position share one upstream fetch. Signed-in users may also attach a Chess.com public username validated through the Published Data API; it stores no credentials and is not proof of ownership because generally available Chess.com OAuth does not exist. The Public/My Games selector remains visible while signed out, but data views prompt for Google sign-in and the appropriate linked chess account; the UI no longer accepts or stores a pasted personal Lichess token.

### Original Phase 2/3 concerns (resolved; wording retained historically)
The explicit-line layer, composed profiles/modules, and both selected-position
drill modes described below have shipped. They remain here as design history,
not unfinished gates. Their future-tense wording records the original concerns:
- **Position-keyed repertoire storage may be causing repertoire-building friction.** The current normalized-FEN keyed model is good for transpositions, but it may be making some authoring/editing flows harder than expected. Re-evaluate whether the UI/state model needs an additional move-order/tree-path layer on top of the FEN graph before building player-data import/deviation analysis on it.
- **Multiple saved repertoires with overlap and overlays.** Defer this until true backend persistence exists. Once repertoires are backend-backed, users should be able to create multiple separate repertoire profiles/collections that may overlap in positions and lines, then select multiple repertoires to overlay in the explorer/drill views.
- **Drill from selected position.** Users should be able to start drills from a selected repertoire/explorer position. When doing so, include only drills/leaf lines that pass through that position. Provide two drill-start modes: (1) skip straight to the selected position for every drill, or (2) start from move 1 so the user still gets reps for the line leading up to that selected position.

- [x] **Phase 2 — Repertoire builder**: FEN-keyed repertoire tree per color (normalized-FEN identity for transpositions), built directly into the explorer page (own-move-only save toggle in the move list that cascades to save every earlier ply including opponent replies, saved continuations merged into the same move-list grid, Lichess-explorer annotation), `localStorage` persistence. Toggling White/Black repertoire resets the board. Opponent replies may branch without limit; repertoire-side positions enforce one response per module, while overlapping modules in a profile may still provide alternatives.
- [x] **Phase 3 — Drills (Chessly-style)**: a Drills mode alongside the explorer, isolated from explorer/repertoire-editing state. A drill session enumerates one "line" per leaf (root-to-leaf path) of the repertoire tree for the active color — leaf count is additive across branches, not multiplicative, so multiple saved options at a branch point don't blow up the drill count or force a single "correct" answer: any saved move is accepted if it still leads to a not-yet-completed branch, and playing an alternate valid option redirects the session onto that branch instead of failing, while the abandoned branch stays queued for a later pass. If the user chooses a saved move whose branch has already been fully completed during the current session, the move is rejected and snapped back without counting as a failed drill, forcing practice of the still-pending branch. Progress is tracked per leaf (not per occurrence) via a pending set, with a live "Drill X of Y" readout; after choosing "Retry failed", the retry pass only counts failed lines and reads "Retrying failed drill X of Y." The target line is deliberately not shown, since that would spoil the drill. Presentation order is shuffled automatically when starting, restarting, and retrying; the manual “Shuffle drills” control reorders upcoming drills without resetting the active occurrence or recorded results. The user's own move and its auto-played opponent reply are applied as two separate state transitions, not one (`pendingAutoPlayStep`/`advanceAutoPlay` in `drillSessionLogic.ts`), with `useDrillSession` re-applying the opponent's reply ~320ms later - long enough for react-chessboard's own move animation (300ms) to finish - so the board animates each ply individually instead of jumping two plies at once, which read as an abrupt jump rather than a smooth slide. Completing a drill line pauses at the final position, plays the drill-complete sound, gives a calibrated Stockfish verdict (equal/slight edge/clear advantage/winning or forced mate), draws an orange arrow for the engine's recommended continuation, shows its principal variation, and waits for the user to choose "Next drill" or "Finish" before advancing. Once the Lichess sample arrives, up to three blue arrows also show common empirical continuations with opacity based on frequency; these are explicitly labeled as game statistics rather than engine recommendations or semantic strategic themes. That review also brings in the two per-position views the explorer has, for the position the line ended in: the engine's evaluation (an eval bar beside the board, plus score/depth in the panel) and the Lichess explorer statistics, rendered read-only since the board is paused. Both are deliberately scoped to the pause - a live eval bar or move statistics mid-drill would hint at the prepared move - and the explorer request is skipped outright for every position walked through on the way (`useExplorerStats`'s `enabled` flag) rather than fetched and hidden. Since drill positions are keyed by normalized FEN, the leaf is expanded back into a complete FEN first (`denormalizeFen`, taking the move number from the tracked leaf ply) before it's handed to Stockfish or the Lichess explorer. Wrong moves (legal but unsaved) are classified via a one-shot Stockfish comparison of the position before/after the move, using a 50 centipawn-loss threshold to distinguish objectively bad moves (shown with the engine's best-response line) from merely off-book ones; the board holds the resulting wrong position for about one second before reverting to the pre-move position, and repeated wrong attempts at the same position progressively reveal the correct move's origin square (2nd attempt) and destination square (3rd+). A Hamming-distance-based position-similarity check (`positionSimilarity.ts`) flags when a near-identical position elsewhere in the repertoire has the played move saved, as a transposition hint. Mistake tracking is intentionally simple for this phase: session-scoped (not persisted) perfect-vs-failed tracking per line, shown in an end-of-session summary with a "Retry failed" action. Core session logic (`drillSessionLogic.ts`, `repertoireDrills.ts`, `positionSimilarity.ts`, `moveQuality.ts`) is unit-tested with Vitest.
  - **Current completion-review behavior (supersedes the older empirical-arrow description above):** completion never auto-scrolls. View in explorer, Next/Finish, Analysis, Stats, Shuffle drills, and Restart are directly below the board; Analysis and Stats are collapsed by default, and clicking either scrolls to it without toggling it closed. The depth-24 MultiPV3 cache is the only completion engine source, but complete three-line snapshots stream during iterative deepening so the board does not wait for depth 24. The eval/verdict continue updating, while arrows refresh only at depth 8/16/24 milestones to avoid flicker. Lichess data appears only inside the explicitly expanded Stats view and does not drive review arrows.
  - End-of-line continuation arrows now include several future branches: orange is Stockfish's immediate choice, blue is common immediate Lichess play, and green combines the player side's common next moves after each of the three leading immediate replies. The green frequency is weighted across both plies and identical replies are deduplicated.

- [x] **PGN import/export** (cross-cutting, not a phase): export a per-color repertoire tree as PGN movetext with RAV variations for every saved branch point (`frontend/src/lib/pgnExport.ts`), and import a PGN (with or without variations) back in (`frontend/src/lib/pgnImport.ts`), both wired into a `PgnImportExportPanel` in the explorer's side column. Import uses a hand-rolled recursive-descent movetext tokenizer rather than chess.js's single-mainline public PGN API.
